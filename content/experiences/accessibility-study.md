## 목적

프롬프트를 잘 쓰는 데서 끝나지 않고, 원하는 결과가 실제 화면까지 이어지는지 확인하는 방법을 고민했습니다. 네이버 블로그 자동화를 사례로, 글의 목적을 작성 기준과 QA 항목으로 연결했습니다.

## 의도

- **목적을 확인 가능한 기준으로:** 누구에게 무엇을 전달할지 먼저 정했습니다. 예를 들어 ‘비개발자도 이해할 수 있게’라는 목적을 ‘낯선 용어를 풀어 쓰고, 구체적인 예시를 넣기’로 바꿔 작성과 검토에 함께 사용했습니다.
- **원고와 화면을 구분해서 QA:** 원고의 문장이 맞아도 편집기에 옮긴 뒤 제목이 중복되거나 목록 들여쓰기가 달라질 수 있습니다. 글자 수·중복은 검사 스크립트로, 제목·문단 순서·서식은 편집기 화면에서 확인하도록 나눴습니다.
- **반복 탐색은 줄이고, 상태 확인은 남기기:** 처음 찾은 입력란과 버튼의 DOM 탐색 규칙을 재사용하도록 설계했습니다. 다만 저장한 규칙을 그대로 믿지 않고, 예상한 편집기 상태와 다르면 입력을 멈추고 해당 단계부터 확인하도록 했습니다.

## 성과

- **재사용 가능한 작업 흐름:** 원고 작성·부분 수정·로컬 검사를 스킬로 정리하고, 편집기 입력과 화면 검토에 사용할 제어 지침을 함께 구성했습니다.
- **FE 관점의 학습:** 프롬프트와 QA는 같은 완료 기준을 공유해야 한다는 점을 배웠습니다. 데이터가 맞는지뿐 아니라 사용자가 보는 화면도 의도에 맞는지 확인하고, 발견한 차이를 다음 요청에 반영하는 관점으로 이어졌습니다.

**사례 · 네이버 블로그 편집기 제어 설계**

**최초 DOM 탐색·매핑 → 저장한 규칙으로 묶음 입력 → 필요한 항목만 QA**

재사용하는 것은 DOM 전체의 복사본이 아니라, 제목·본문·서식 도구를 역할과 라벨로 찾는 규칙입니다. 로컬 UI 프로필을 지원하는 환경에서는 페이지 주소·프레임·화면 크기도 함께 저장해, 같은 편집기 맥락에서 규칙을 적용하도록 설계했습니다. 입력 후에는 제목 일치·문단 순서·누락 여부를 확인하도록 했습니다.
